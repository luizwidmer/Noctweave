# Noctweave Dependency SBOM And Release Policy

Last updated: October 30, 2026

This document records the current software bill of materials and the minimum release checks for the public Noctweave core, CLI, and relay tooling. It is a project-maintained SBOM, not an independent vulnerability assessment. The native machine-readable snapshot is `noctweave_sbom.json`, and the interoperable CycloneDX JSON export is `noctweave_cyclonedx_sbom.json`; both are generated by `scripts/generate-sbom.py`. The standalone [NoctweaveJS repository](https://github.com/luizwidmer/NoctweaveJS) owns its JavaScript dependency and release checks.

## Scope

- `NoctweaveCore`
- `NoctweaveRelayServer`
- `NoctweaveCLI`
- optional `NoctweaveSecurityKeys` library and `NoctweaveSecurityKeyBridge` app-unlock helper
- source-built Electrobun relay desktop launcher
- Docker relay image
- optional Reticulum transport bridge and its independently built image

## Desktop Packaging Dependencies

The optional source-built relay launcher uses dependencies pinned in its
`bun.lock`:

The source tooling requires Bun 1.4.4 or newer. Earlier Bun 1.3.14 was affected
by the October 2026 [Brotli decoder](https://github.com/oven-sh/bun/security/advisories/GHSA-663w-cv8g-jj2p),
[TLS trust store](https://github.com/oven-sh/bun/security/advisories/GHSA-26q8-h657-pf84),
and [HTTP/3 QPACK](https://github.com/oven-sh/bun/security/advisories/GHSA-cf8x-9m69-3gg3)
advisories. `package.json` sets the minimum engine and the release verifier
rejects an older local Bun before install or audit. Electrobun 2.0.5 embeds
the patched Bun 1.4.4 runtime for packaged launchers. The desktop build checks
the bundled runtime version in artifact metadata. Prepare, build, dev, and watch
also reject an older host Bun before spawning Electrobun, then use an owner-only local
Hutch toolchain cache on POSIX. Windows uses a dedicated path under
`LOCALAPPDATA`; ACL validation is not automated. Hutch otherwise executes a
cached Bun before verifying its hash.

| Package | Version | Purpose |
| --- | --- | --- |
| `electrobun` | `2.0.5` | Packages the client and relay launcher with system WebViews. |
| `@resvg/resvg-js` | `2.6.2` | Renders the relay SVG icon to an alpha-preserving PNG. |
| `png2icons` | `2.0.1` | Produces ICNS and ICO variants from the generated PNG. |
| `typescript` | `7.0.2` | Type-checks the desktop launcher source. |

Electrobun 2.0.5 no longer resolves the former `ip-address` proxy dependency.
The release verifier rejects a vulnerable version if that dependency returns.

The machine-readable SBOM inventories every exact package/version pair in
`bun.lock`, including platform-specific and transitive packages, rather than
only the direct packages listed above.

The optional Reticulum sidecar uses `python:3.13-alpine` and is built separately
from the default relay image. Building it installs the fully pinned Python
requirements, including `rns`, and therefore accepts the upstream Reticulum
License boundary. Do not merge it into the standard relay image or describe it
as an AGPL dependency.

Every shipped Docker base is pinned by SHA-256 digest. Updating a tag or digest
requires a fresh multi-scanner image/config pass and corresponding SBOM update.
On October 30, 2026, daemonless Trivy 0.76.1 scanned the old and replacement
base digests and Grype 0.121.0 independently checked the coturn replacement.
The old coturn and Caddy bases carried Brotli 1.2.0, affected by
CVE-2026-111497, and the replacement tags still contain that package before
the Dockerfile's full `apk upgrade`. Alpine v3.24 publishes Brotli 1.2.1-r0.
The old Ubuntu runtime base carried a fixed-in-repository OpenSSL package
finding; the replacement Ubuntu digest had no high or critical Trivy findings.
The replacement Python base had no Alpine OS findings. These are base-image
results, not scans of the final built images. Docker became available during
the follow-up audit. The four final `linux/arm64` images were rebuilt without
cache and scanned with a fresh Trivy vulnerability database. Each scan had an
installed OS package inventory and zero HIGH or CRITICAL findings. Caddy's Go
binary and Reticulum's Python dependencies had language package inventories;
Trivy does not inventory modules embedded in the Swift relay binary. Caddy and
coturn installed `brotli-libs` 1.2.1-r0, confirmed both by the scan inventory
and `apk`. The relay had 23 MEDIUM and 16 LOW Ubuntu OS findings with no
upstream fixed versions listed in that scan. Caddy had one UNKNOWN OpenPGP
advisory in `golang.org/x/crypto`; package presence is confirmed, but
reachability through the deployed relay route was not demonstrated. The scan
lists no fixed version for it. These are bounded scan results, not an all-clear for
Swift or vendored binaries. The default `linux/amd64` release gate remains
required before distributing an amd64 image.

Caddy's dependency graph retains `go-jose/v3@v3.0.5` through Smallstep, and
upstream has no patched v3 release for CVE-2026-116585, CVE-2026-116586, and
CVE-2026-116587. `CaddyPatches/` records source-backed backports and focused
regression tests for all three. The Docker build applies the patch to a
checksum-verified v3 source copy and uses that copy in the final Caddy binary.
Because Trivy reports this local replacement as an unversioned development
module, the release gate checks the patch digest and final binary build-info,
and separately scans the unpatched v3.0.5 dependency as an advisory sentinel.
Any new v3 advisory blocks the gate until reviewed and addressed.

The final filesystem scan covers active source and package manifests. It
excludes retained `.runtime` and `ReleaseArtifacts` history, private build
caches, the local `NoctweaveCore/liboqs` source checkout, and the deliberately
vulnerable go-jose sentinel. That liboqs checkout contains upstream Python CI
and code-generation requirement files with current advisories; Noctweave's
reviewed CMake build paths do not install or execute those Python tools. The
sentinel is scanned and enforced separately. These exclusions are explicit in
`scripts/verify-release.sh`, and the final images are scanned independently.

## Dependency Audit Procedure

Before a release, run the local verifier:

```bash
scripts/verify-release.sh
```

It verifies the pinned liboqs 0.16.0 source and packaged headers, generates a
candidate SBOM and checks that the committed snapshots are current, checks
Swift and Bun package resolution, audits the resolved Bun graph, runs the Linux
relay test suite, then requires a running Docker daemon and Trivy to build and
scan the final relay, Caddy, coturn, and Reticulum images. The container gate
downloads a fresh vulnerability database, checks that each report identifies
the image Docker just built, rejects high and critical findings, and checks
both the installed-package inventory and `apk` for Brotli >=1.2.1-r0 in the
Caddy and coturn images. It verifies Caddy's actual Go module inventory, the
local go-jose/v3 patch and upstream advisory sentinel, adapted HTTP routes,
and each image's configured non-root user. A missing tool, daemon, build, scan, or package
inventory fails the release check. Standalone container checks keep reports at
the printed temporary path. The parent release check removes its temporary
reports on exit; set `NOCTWEAVE_CONTAINER_SCAN_OUTPUT_DIR` to retain them.

Run `scripts/verify-container-release.sh` on its own to check only containers.
It checks `linux/amd64` by default; set `NOCTWEAVE_CONTAINER_PLATFORM=linux/arm64`
and rerun for an arm64 release. Run the gate separately for each architecture
you distribute. High or critical findings require a fixed dependency or a
reviewed, source-backed exception to the release policy and gate; there is no
environment-variable bypass. Record any exception's CVE, affected package and
version, reachability analysis, reviewer, and expiry in the release evidence.

The public repository does not ship binary release automation or an official
prebuilt relay desktop application. Maintainers and downstream users build the
Electrobun relay application from source on each target operating system. The
relay launcher then builds its Linux relay image locally
from the source snapshot packaged with that build. Before tagging a release
candidate, maintainers must still run this verifier and attach the generated
native and CycloneDX SBOM snapshots plus locally generated artifact checksums to
the release notes. CI for relay tests, container builds, and scanner evidence
remains a separate roadmap item.

Manual equivalent:

1. Refresh and verify the machine-readable SBOM:

```bash
scripts/generate-sbom.py
git diff --exit-code "NoctweaveDocumentation/noctweave_sbom.json"
git diff --exit-code "NoctweaveDocumentation/noctweave_cyclonedx_sbom.json"
```

2. Run package resolution from a clean checkout:

```bash
cd "NoctweaveRelayServer"
swift package resolve
git diff --exit-code Package.resolved
```

3. Confirm direct package versions still match `Package.swift` exact pins:

```bash
swift package show-dependencies
```

Then verify the desktop lock and advisory state:

```bash
bun install --frozen-lockfile --ignore-scripts
bun audit
git diff --exit-code package.json bun.lock
```

4. Build and test the relay:

```bash
swift test
swift build -c release
```

5. Rebuild the Apple XCFramework from the reviewed source checkout:

```bash
git clone https://github.com/open-quantum-safe/liboqs.git NoctweaveCore/liboqs
git -C NoctweaveCore/liboqs checkout 5a1a854b0dc9f2141bdc771c555ee60c37950183
scripts/build-liboqs-xcframework.sh
```

The build script refuses a modified checkout or any revision other than the
central pin in `scripts/liboqs-version.sh`.

6. Build the Docker image with the reviewed `liboqs` version and immutable commit:

```bash
docker build \
  --build-arg LIBOQS_VERSION=0.16.0 \
  --build-arg LIBOQS_COMMIT=5a1a854b0dc9f2141bdc771c555ee60c37950183 \
  -t noctweave-relay:<version> "NoctweaveRelayServer"
```

7. Record final artifact hashes:

```bash
shasum -a 256 <artifact>
docker image inspect noctweave-relay:<version> --format '{{.Id}}'
```

8. Review upstream security advisories for:
   - YubiKit Swift when shipping the optional app-unlock library/helper
   - SwiftNIO
   - Swift Crypto
   - Open Quantum Safe `liboqs`
   - Docker base image packages
   - every package resolved in the relay desktop `bun.lock`
   - Reticulum `rns` when the optional sidecar is distributed

9. Review `noctweave_core_stability_policy.md` and record any source, CLI,
   wire-format, persisted-state, Docker-flag, or relay API compatibility changes
   in release notes.

## Release Packaging Policy

Every release should have:

- SHA-256 checksums for generated documentation and release archives.
- Docker images pushed by digest and tagged immutably if public relay images are offered later.
- Release notes that identify dependency changes, cryptographic dependency changes, and any deliberate storage/schema reset requirements.

Cryptographic dependency updates require a dedicated release note section and should not be bundled silently with unrelated changes.

Public `NoctweaveCore` releases must also follow the compatibility rules in
`noctweave_core_stability_policy.md`.

## Red Flags

Do not release if:

- `Package.resolved` changed unexpectedly.
- `package.json` and `bun.lock` disagree, `bun audit` fails, or the desktop
  graph regresses below a documented security floor.
- `liboqs` changed without explicit review.
- Docker base image changed without a vulnerability and compatibility review.
- Tests skip unexpectedly beyond the documented opt-in live TLS relay test.
- SBOM generation or release verification fails.

## Distribution Notes

- Repository verification remains scoped to dependency inventory, package pins,
  protocol tests, and optional scanner hooks. Those checks support development
  hygiene; they are not a substitute for downstream application provenance.
- Docker relay publishing is an operator packaging concern. If public images are
  introduced later, document tags, immutable digests, and vulnerability scanning
  in the relay operations guide.
